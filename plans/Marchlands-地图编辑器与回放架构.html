地图编辑器
与回放

当前代码已经有三件关键资产：确定性模拟、MapDef 校验、基于命令的回放雏形。它们足够支撑一个图结构地图编辑器与本地回放文件，但还缺 MapDocument、回放文件格式、编辑器视口和宿主文件接口。

判断

有基座，但还没有现成的编辑器与回放产品。

图结构地图编辑器和命令级回放可以直接在这套模拟上长出来；自由瓦片地形编辑器不能。

不要重写模拟核心。先补三条边界：MapDocument、回放文件、Electron 文件接口。
01

结论

先回放，后编辑器。回放是低风险、可验证的基座加固；编辑器是更大的交互产品。两者共用同一套 MapDef 和确定性模拟，但不要把编辑器塞进实时对局循环。

现在能做

图结构地图编辑器

拖放城镇、粮仓、驻兵点，连接公路，设置归属、等级、驻守状态，编译成合法 MapDef，进入试玩。

现在不能直接做

自由瓦片地图

任意地形块、道路笔刷、建筑自由摆放、网格寻路，需要新的地形模型和寻路编译器。

三条不变量

  1. 编辑器只改 MapDocument。MapDef 是编译产物，模拟只读 MapDef，永远不接收编辑器里的临时对象。
  2. 回放存命令，不存视频。文件包含地图、生效规则、种子、全部命令与哈希检查点，播放时重新推进模拟。
  3. 文件访问只走 Electron 主进程。渲染层不直接拿任意路径，主进程负责对话框、读写和路径白名单。
先修一个具体问题

实时对局会把规则速度乘以 0.7，见 session.ts 的 slowRules。如果回放使用原始规则推进，兵团的到达 tick 会不同，最终哈希对不上。回放必须记录生效后的规则，或者在记录前移除这层减速。

推荐顺序

如果只能先做一件事，做 P0 与 P1。它会立刻给编辑器提供回归工具；编辑器试玩产生的对局也能被回放验证。

适合的编辑器节点与公路组成的领地沙盘，20 到 40 个据点，强调路线选择。
不适合的编辑器模拟城市式瓦片堆叠。模拟核心没有地形网格、碰撞与格子寻路。
关键取舍先做可玩、可验证的图编辑器，再决定是否投资自由地形。
02

现有基座

基座比表面看起来强。模拟层已经具备确定性、固定步长、状态哈希和命令入口；内容层已经有地图校验。缺的是编辑器与回放之间的“产品层”。

能力现状结论
确定性模拟step(state, commands)，20Hz，纯 TypeScript，无 DOM 与文件系统依赖；canonicalState 可校验。可直接复用
地图格式MapDef 包含据点、边、玩家、目标；validateMap 校验连通性、叶子据点、驻兵点监视边与边长。可直接复用
命令回放harness 的 Replay 已记录 tick、命令、检查点与结果，并能在相同种子下复算。只有雏形
实时对局GameSession.tick 组合 AI、玩家命令、模拟推进、场景与 HUD；实时规则被减速。需要拆分
3D 场景BattleScene 直接从 SimState 构建城市与道路，私有方法多，没有编辑器需要的屏幕到地面反投影。需要抽取视口
建筑资产八类建筑模型与三级规格已经存在，但模拟只认城镇、粮仓、驻兵点三种据点。先做视觉映射
文件宿主preload 只暴露窗口大小、全屏和退出，没有地图或回放文件对话框。需要扩展
最强的地方

模拟不依赖浏览器，命令在 tick 边界进入，种子与规则显式传入。只要把这三件事记录完整，回放不需要“录像”，也不需要 AI 重跑。

最薄的地方

实时对局把输入、AI、模拟、场景、HUD、音效和结束回调都塞在一个 GameSession 里。回放如果复制这一整套，会得到第二套难维护的运行时。

证据文件createGame · step · hash
回放雏形replayMatch 已经证明同种子复算可行。
地图入口App 仍以静态 import 加载地图，运行时没有地图目录。

04

地图编辑器

当前模拟的地图是图结构：据点是节点，公路是边。编辑器的第一版应该尊重这个事实。拖拽体验可以像摆放素材，但底层产物必须是一张合法的 MapDef。

推荐

图结构编辑

拖放据点，拉线连接公路，设置属性，编译时自动算边长。直接兼容现有寻路、驻兵点监视边与胜负判定。

暂缓

瓦片地形编辑

地形块、道路笔刷、建筑占地、网格寻路。需要新的地图模型与寻路编译器，不是加一个面板能解决。

03属性与规则

MapDef 校验

MapDocument

MapDocument 是编辑器的唯一真相。它比 MapDef 多一些作者信息，少一些运行时字段。保存 MapDocument，加载时编译成 MapDef；回放内嵌编译后的 MapDef。

interface MapDocument {
  schema: 1;
  slug: string;
  name: string;
  size: [number, number];
  biome: string;
  players: MapPlayer[];
  sites: SiteDraft[];
  roads: Array<{ from: string; to: string }>;
  objectives: MapObjective[];
  transit?: "open" | "friendly";
}

interface SiteDraft {
  id: string;
  kind: "town" | "granary" | "outpost";
  owner: 0 | 1 | 2;
  level: 1 | 2 | 3;
  pop: number;
  pos: [number, number];
  stance?: "evade" | "engage";
  watch?: [string, string];
  visual?: BuildingKind; // 只影响渲染，不进入模拟
}

compileMapDocument(doc) 负责生成稳定 ID 检查、边去重、边长计算、叶子约束、驻兵点监视边和连通性诊断，最后交给 validateMap。编辑器只展示诊断，不复制校验规则。

交互与场景

  • 调色板：城镇、粮仓、驻兵点三组；每项带默认等级、人口与模型预览。
  • 放置：拖到地面，吸附网格与已有据点；禁止重叠与越界。
  • 连线：从据点拖到另一个据点；特殊据点只能有一条边，驻兵点必须在相邻公路中选监视边。
  • 属性：归属、等级、人口、驻守状态、监视边、显示名与视觉模型。
  • 撤销：编辑命令栈，移动合并为一次，删除保留引用恢复。
  • 试玩：编译并校验后进入实时对局，退出时保留草稿与镜头。
  • 诊断：错误阻止试玩与导出；警告允许继续。
场景不要直接复用 GameSession

GameSession 需要 SimState、HUD、AI、音效与结束回调。编辑器需要的是没有对局状态的 MapViewport。建议先把 BattleScene 中的地面、道路、建筑、相机与投影抽成 WorldView，再让实时对局与编辑器各自组合。第一版可以复制少量渲染逻辑，但不要复制对局循环。

建筑模型怎么用

当前模拟只有三种据点，八类建筑模型是表现资产。建议在 MapDocument 与 MapDef 上增加可选 visual 字段，渲染器按它选模型，模拟仍然按 kind 执行。这样编辑器可以把步兵营、弓箭塔、矿区摆上地图，而不用先写八套玩法。

如果这些建筑要有独立功能，例如兵营产兵、矿区产金，那是新的机制层：需要新的 SiteKind、规则、AI 评分与胜负条件。不要在编辑器阶段偷偷塞进去。

保存与目录

  • 官方地图只读；编辑器打开时复制为草稿。
  • 用户地图保存到 app.getPath("userData")/maps，使用 .mlmap.json 的 MapDocument JSON。
  • Electron 主进程负责打开、保存、另存为、列出地图；渲染层只拿数据与摘要。
  • 浏览器开发模式用文件上传与下载作为降级。
  • 自动保存到 localStorage，显式保存才写入文件。

MVP 边界

第一版只做：放置三类据点、连线、属性、撤销、诊断、试玩、保存与加载。不做：瓦片地形、道路曲线、建筑独立功能、地图内脚本、多人协作、在线工坊。

验收地图20 个据点，至少 2 座城镇，图连通，特殊据点均为叶子，驻兵点监视边合法。
核心测试同一 MapDocument 编译两次得到完全相同的 MapDef；移动据点后边长自动重算。
性能预算20 到 40 个据点，拖动只移动幽灵；提交编辑后重建场景，目标 <100ms。
05

回放

回放不是录像文件，而是“可重新执行的命令日志”。模拟是确定性的，15 分钟一局只需要地图、规则、种子、命令和少量哈希检查点。

记录每个 tick 的
玩家与 AI 命令
封装地图、规则、种子
检查点、结果
校验重放并比对
tick 哈希
播放时间轴、速度
镜头与选中

文件格式

interface ReplayFile {
  format: "marchlands.replay";
  version: 1;
  createdAt: string;
  engineVersion: string;
  map: MapDef;
  rules: Ruleset; // 必须是生效后的规则
  seed: number;
  commands: Array<{
    tick: number;
    source?: "p1" | "p2" | "ai";
    commands: Command[];
  }>;
  checkpoints: Array<{ tick: number; hash: string }>;
  result: {
    status: "playing" | "finished";
    winner: 0 | 1 | 2;
    reason: string | null;
    ticks: number;
    finalHash: string;
  };
}

记录点

  • tick 边界：在 step(state, commands) 之前记录 state.tick 与合并后的命令，顺序不变。
  • 全部命令：玩家指令与 AI 指令都记录。回放不重跑 AI，这样 AI 版本变化不会破坏老回放。
  • 生效规则：记录 slowRules 之后的规则，而不是原始 content 规则。
  • 地图快照：直接内嵌 MapDef，用户删掉自定义地图后回放仍可打开。
  • 检查点：每 100 tick 记录一次哈希，最终再记一次；用于发现版本或文件损坏。
为什么不做快照

一局 18,000 tick 的完整复算在 harness 里是几十毫秒量级。第一版每次跳转都从头复算即可，文件更小、格式更稳。等地图规模显著变大，再加稀疏状态快照。

播放器

  • 载入后校验格式、地图、规则与命令上限；不合法直接拒绝。
  • 从种子创建初始状态，按 tick 应用记录命令；到达检查点就比对哈希。
  • 播放控件：播放、暂停、0.5 到 4 倍速、时间轴、逐 tick、跳到检查点。
  • 回放模式禁用派兵、升级、改道与切换驻守；镜头、缩放与选中保留。
  • 时间轴拖动时复算到目标 tick；向后跳转从最近检查点或起点重来。
  • 结果页提供“保存回放”，菜单提供“载入回放”；扩展名为 .mlreplay.json。

运行时拆分

最小改动不是重写 GameSession，而是把 tick 内“生成命令、推进模拟、消费事件”抽成可复用的 MatchRuntime，场景与 HUD 留在表现层。实时模式和回放模式各自提供命令来源：实时来自输入与 AI，回放来自文件。

// 目标形态
LiveMatch   = InputSource + AISource + MatchRuntime + MatchView
ReplayMatch = ReplaySource + MatchRuntime + MatchView

如果第一版不想大改，可以先在 GameSession 内加 Recording 钩子并复制一个 ReplaySession。它能工作，但会留下两套 HUD 与事件处理；建议把复制限制在 P1，P2 再收敛。

校验与兼容

  • 文件带 version 与 engineVersion；不兼容时给出明确提示，不静默播放错误结果。
  • 哈希算法变更时提升 hashVersion；老回放仍可作为“只读录像”打开，但不承诺哈希通过。
  • 地图与规则都通过现有 content 校验；拒绝超大文件、超长命令数组与非法 tick。
  • 回放文件默认本地保存，不上传服务器；在线分享是后续产品决策。
文件大小地图约 4KB，规则约 2KB，命令与检查点通常不到 100KB。
失败模式哈希对不上时不要继续假装正常播放；显示版本或数据错误。
直接收益回放可以回归模拟、复现 bug、验证编辑器试玩，比录屏更有用。

实施路线

按一名开发者估算，做到可用的编辑器与回放闭环大约 4 到 6 周。真正的大头是编辑器交互与文件宿主，不是模拟。

P0

回放采集与文件格式

新增 replay 包的记录器与编解码；实时对局记录生效规则、地图、种子、全部命令与检查点；结果页导出文件；harness 改用共享类型。

2 到 3 天
P1

回放播放器

载入、校验、播放、暂停、倍速、时间轴、逐 tick、哈希检查；菜单入口与结果页保存；抽取最小 MatchView 复用场景与 HUD。

3 到 5 天
P2

纯逻辑包：草稿类型、编辑命令、撤销、编译、诊断、导入导出；用 20 据点地图与非法地图做单测；不碰 UI。

4 到 6 天
P3

编辑器 MVP

编辑器页面、WorldView、调色板、拖放、吸附、连线、属性面板、诊断、撤销、自动保存、试玩与返回。

8 到 12 天
P4

宿主与自定义地图

4 到 6 天
P5

表现扩展

视觉建筑映射、道路装饰、地图缩略图、回放分享卡片；暂不做自由地形与在线工坊。

按需
为什么不先做编辑器

编辑器会立刻遇到“试玩结果是否可复现”的问题。先把命令记录与回放闭环做完，编辑器每次试玩都自带可验证的回归样本；否则后面还要补一套调试设施。

验证策略

  • MapDocument：同一文档编译两次必须字节级一致；移动据点后所有关联边长自动重算；非法引用必须给出可定位诊断。
  • 回放：固定一局 15 分钟黄金样本，每个检查点与最终哈希一致；删掉 AI 决策代码后，老回放仍能完整播放。
  • 编辑器：用 20 据点与 40 据点两张草稿做编译、保存、重载、试玩；拖动、连线、撤销与试玩返回都不丢状态。
  • 端到端：在打包后的 EXE 中创建地图、保存、重开、试玩、保存回放、载入回放；浏览器开发模式保留文件上传与下载降级。

第一刀

  1. 抽出 ReplayRecorder，在 GameSession 的 tick 边界记录命令与生效规则。
  2. 定义 ReplayFile v1，完成导出、载入、复算、哈希校验。
  3. 用一局 15 分钟对局做黄金样本，之后每次改动都跑回放测试。
07

风险与边界

风险后果处理
生效规则未记录回放中兵团到达 tick 与实时不同，哈希失败。记录 slowRules 后的规则；加一条单元测试专门覆盖。
地图或规则漂移内容更新后老回放无法复现。回放内嵌 MapDef 与 Ruleset；文件带 schema 与版本。
AI 版本变化重跑 AI 会改变命令。记录全部命令，回放不重新决策。
编辑器引用失效删据点后边、监视边、所有权悬空。所有编辑走命令栈；删除时级联清理或阻止；编译期诊断。
场景与对局耦合编辑器拖拽卡顿，或复制出第二套 HUD。抽 WorldView；拖动只移动幽灵，提交后重建；不复制对局循环。
自由地形范围失控编辑器变成另一个项目。第一版锁定图结构；瓦片地形另立项目，先做可行性原型。
文件安全渲染层读写任意路径，或载入恶意 JSON。路径由主进程对话框决定；大小上限与 schema 校验；原子写入。
回放兼容性旧文件在新版本中算错，用户误以为作弊。版本与哈希校验；失败时只读展示，不声称可验证。
大地图性能40 个以上据点时，每次编辑重建场景变慢。先测 40 据点；必要时按层增量更新；不要过早优化。
命令归属不清改道或升级命令缺少玩家来源，回放审计困难。回放记录 source 元数据；后续再考虑把 player 加入模拟命令。
08

需要拍板

下面五个决定会改变架构。我的默认建议如下。

地图编辑形态：图结构，还是自由瓦片？

建议图结构优先。 先做能直接进入现有模拟的编辑器；自由瓦片另做原型，证明寻路与性能后再投入。

八类建筑：只做视觉，还是各自有玩法？

建议先做视觉映射。 MapDocument 增加可选 visual 字段，模拟仍按三种 kind 执行；兵营、矿区等功能后续单独设计。

编辑器面向玩家，还是内部工具？

建议游戏内页面，保存到用户目录。 官方地图只读；玩家地图与回放都在本地，不依赖服务器。

回放先做，还是编辑器先做？

建议回放先做。 它是更小的确定性投资，也是编辑器试玩的验证工具。编辑器数据层可以在 P1 期间并行设计，但 UI 不要抢在回放前面。

回放只存本地，还是做在线分享？

建议先本地文件。 在线分享需要账号、存储、审核与防盗链，不属于当前 M1 范围。

建议的下一步

先批准 P0：只做回放记录器与文件格式，不改 UI。产出是一局可导出、可复算、哈希一致的对局。这个结果会直接告诉我们基座是否真的足够，然后再投入编辑器。
