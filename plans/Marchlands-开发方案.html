00

摘要

首轮只做一张地图：forest01。目标不是展示系统，而是让一个玩家从主菜单进去，打完一局，能赢能输，能重开，所有页面正常。Agent、服务端、新机制都后移。

决策选择理由
首轮内容forest01，7 城，1 人类 + 1 AI最小的一张图，2 个玩家，5 个中立城；能完整走完占领、升级、胜利/失败。
画面全 3D 低模，4 个 90° 方位；另做 3 节点高低差测试场景forest01 本身没有高度层；3D 管线先跑通，高低差用测试场景验证，正式图放 forest09。
架构sim + 客户端；确定性核心保留，但不接 Agent先把单机跑稳；Agent 需要协议、观察、回放，第二阶段再加。
系统城镇、中立城、派兵、战斗、升级、胜负只实现 forest01 需要的系统；塔、城堡、铁匠铺、马厩、法术全部后移。
页面启动、主菜单、简报、对局、暂停、结算、设置一局游戏的完整路径必须没有断头路；页面正常本身就是首轮验收项。
Agent第二阶段首轮不实现 MCP/HTTP；等单机可玩、数据稳定后再接。
服务器第三阶段首轮本地存档、本地回放；账号、榜单、校验后面再做。
机制ruleset 1，只复刻新机制会污染“能不能完成一局”的判断；全部放 ruleset 2。

首轮验收只看六条

能从主菜单开始一局、能赢能输、能重开、页面不重叠不报错、目标机 60 帧、3 节点高低差场景能跑。六条全过，才进入第二张地图；任何一条不过，先修。

三个判断

先完成，再扩展一局完整的 7 城单机，比 5 张半成品图有价值；先证明“游戏能完”。
3D 先搭管线forest01 是平地，但相机、地形、单位、遮挡、层高数据都要在首轮定下来。
Agent 后移首轮不写 MCP；sim 仍然确定性、可回放，为第二阶段留好接口。
01

原作拆解

原作《土地抢夺者》，也就是你说的《土地争夺者》，不是传统 RTS。它把“占点、产兵、再占点”压缩成一局几分钟的攻防，操作只有选城、派兵、升级、放法术。续作要继承的是这个节奏，不是它的贴图。

维度从安装包与脚本中确认的数据
关卡45 关，5 章 × 9 关；另有 1 张多人测试图。单图 7–26 座城市。
生态森林、荒漠、冰峡、群岛、熔岩，共 5 套背景与建筑皮肤。
高度层24/45 关至少有一个高于 0 层的节点；最高 2 层；148/4359 个路径节点、35/848 座城市在高处；森林只有 forest09 有高低差。
玩家每关 4 个玩家槽位，城市归属 0–4；0 为中立，1–4 为四个颜色阵营。
城市848 座；5 种类型：城镇、瞭望塔、城堡、铁匠铺、马厩；最高 5 级。
法术20 个可用法术；单局最多带 5 个；费用 400–2000 金币；有充能时间与持续时间。
地图路径图，4359 个节点；单图 33–153 个节点；城市挂在节点上，部队沿边移动。
难度3 档：中尉、上校、将军；AI 参数写在关卡脚本里。
目标时间关卡脚本的 trophy_time 在 32000–556000 之间；按毫秒读是 32–556 秒，单位仍需动态验证，但可以确定是短局。
资源463 张 PNG、115 个 OGG、133 个 TXT、28 张 JPG；解包后约 179.6 MB。
显示1280×768 视口；1024×1024 背景；脚本为 UTF-16LE。

从二进制里看到的东西

我用 REA 打开了 LandGrabbers.exe。PE、x86、SHA-256 f32e34c4…，Ghidra 只识别出 5 个函数和 8 个字符串，导入表里只有 LoadLibraryA、GetProcAddress、VirtualAlloc 这类加载器 API。换句话说，主程序有壳或自解密，静态逆向的收益很低。

这不影响做续作。关卡脚本是 UTF-16 明文，城市、路径、AI 参数、法术列表都在里面；资源是独立的 PNG 和 OGG。真正需要动态验证的只有战斗公式、人口增长、金币收入这些常量。它们可以用固定种子、改脚本、记录结果的方式反推，不必把 exe 完全拆开。

脚本还给出了 AI 的四个旋钮：attack_delay 10、max_armies_per_attack 2、upgrade_threshold 0.70、panic_threshold 0.90。它们足以做出四档 AI，不需要让 AI 读玩家操作。

对续作的含义

  • 3D 必须进模拟核心。 不是渲染层把 2D 拉高，而是节点自带 layer/height，坡道边连接层，城市底座压平。否则后续加高地机制要重做数据。
  • 1 张图先完成一局。 forest01 只做城镇、派兵、升级、胜负；先证明游戏能从头到尾跑通，再谈 5 图组合。
  • 短局适合 Agent。 8–12 分钟、约 100 次决策，LLM 可以在一次会话里打完；30 分钟一局会把成本和上下文都拖垮。
  • 首轮只复刻。 新机制先写在 ruleset 2 的设计稿里，代码上留扩展点，但不进首轮验收。

3D 与高低差

forest01 没有高度层，所以首轮不能拿它验收高低差。做法是：首轮完成 forest01 的 3D 地形、四向镜头、单位和遮挡；另做一个 3 节点测试场景，包含 layer 0、layer 2、一条坡道和一座高台城，只验证“能不能跑、能不能看”，不参与正式关卡。正式高低差图放到第二阶段 forest09。

如果你希望首轮就跑一张有高低差的正式图，可以把 forest01 换成 forest09，但城市数从 7 增到 19，单局完成风险明显更高。我的建议是先 forest01 完成一局，再用测试场景验证管线。

03

核心玩法

首轮只做 forest01 需要的系统：城镇、中立城、派兵、战斗、升级、胜负。没有法术、没有特殊建筑、没有新机制。

1. 选城单击己方城；选中后显示守军与可派数量。
2. 派兵默认派当前守军的 50%，向下取整，至少 1。
3. 行军与结算沿路径到目标城；到达后一次性结算。
4. 占领与升级打空守军即占领；升级消耗人口，提高上限与防御。
5. 胜负占满 7 城或消灭 AI；时间到按城市数、人口判定。

对局基线

项目首轮基线
人数1 人类 + 1 AI；2 个玩家。
地图forest01；7 座城；单局 8–12 分钟；15 分钟硬上限。
模拟频率20 Hz 固定步长；所有指令在 tick 边界生效。
出兵每座选中城派出当前守军的 50%，向下取整，至少 1。
行军沿路径边移动，基础 60 单位/秒；forest01 全是 layer 0。
战斗攻方兵力 × 攻击修正，对守方兵力 × 防御修正；败方全灭，胜方保留差值。
升级消耗当前最大人口的 50%；等级 +1；最大人口 +25%；防御 +10%；forest01 最高 3 级。
金币首轮只做收入与 HUD 显示，不做消费；每座城 2 + 0.5 × 等级 金币/秒。
胜利占满 7 城或消灭 AI；时间到按 城市数、人口 依次比较。

出兵与战斗

战斗不做微操。部队到达目标城后一次性结算，玩家看到的是“兵力数字对撞”。这样 20 Hz 的模拟足够，后续 Agent 也能用离散指令玩。

A = troops × attack_mod
D = garrison × defense_mod × level_bonus

if A > D:
    capture; remaining = A - D
else:
    defender survives; garrison = D - A

首轮没有塔，所以不需要塔输出项；没有高地，所以不需要地形修正。先把基础结算跑通，第二阶段再加塔、法术和高地。

AI

首轮只做一档 AI：每隔几秒检查一次，能占中立城就占，人口过半就升级，兵力优势就进攻，老家被威胁就回防。目标不是聪明，而是能打完一局、能赢也能输、不会卡死。

  • AI 不读玩家操作，不用额外资源；只用公开状态。
  • AI 至少能完成一次占领、一次升级、一次进攻。
  • AI 卡住超过 30 秒，自动降级为“派兵到最近中立城”，保证对局能结束。

高低差

正式高低差图放到第二阶段 forest09；届时再把高地战斗加成写进 ruleset 2，不在首轮加。

3D 测试场景

3 个节点layer 0 起点、layer 2 高台、一条坡道连接。

这个场景不是关卡，没有胜负和 AI；它只回答“3D 高低差管线能不能跑”。首轮验收时和 forest01 一起看。

美术方向

“桌面沙盘”：地形有厚度，建筑像上过色的木块或铸铁件，单位是小比例玩具兵，UI 像测绘仪器的黄铜铭牌。首轮只做森林一套，不铺第二生态。

首轮屏幕目标：7 座城、4 支队伍、20 个蒙皮单位、3 万三角面、80 draw call 以内。不追求满编，先保证稳定 60 帧。

制作管线

  • 建模。 Blender 4.x 导出 glTF 2.0；1 单位 = 1 米；原点在底座中心；面朝 +Z。
  • 材质。 低模 + 顶点色 + 手绘渐变贴图；阵营色用材质参数。
  • LOD。 建筑 2 级，单位 2 级；首轮地图小，先不做远处 billboard。
  • 地形。 forest01 用手工高度图；城市底座压平；路径走廊平滑。
  • 导入。 森林一个 Asset Bundle；命名 biome_type_tier_variant；CI 检查三角面、材质槽、贴图尺寸。

确定性规则

客户端、服务端、Agent 必须对同一串指令得到同一个结果，否则回放校验和排行榜都不成立。做法不是“尽量注意”，而是把不确定性从核心包里物理移除。

  • 定点数。 位置、速度、人口、金币全部用整数，1 单位 = 1/1024；不用浮点做战斗结算。
  • 固定步长。 20 Hz，所有指令在 tick 边界生效；渲染层做插值，模拟层不知道帧率。
  • 种子随机。 xorshift128+，种子写进回放；核心包禁用 Math.random 与 Date.now。
  • 稳定顺序。 遍历数组，按数字 ID 排序；不用对象键顺序、不用 Set 迭代顺序。
  • 状态哈希。 每 20 tick 计算一次；回放携带规则集哈希、地图哈希、内容版本。
  • 跨引擎测试。 Node、Chrome、Cocos 原生各跑 1 万局随机指令，最终哈希必须一致。

06

Agent 设计

首轮不做 Agent。第二阶段再做本地 MCP，第三阶段上线。下面保留协议与节奏设计，避免以后改核心。Agent 不是“自动战斗”按钮，而是一个没有渲染器、没有鼠标、按决策窗行动的玩家。

六条原则

无渲染可玩模拟核心不依赖 Cocos；Agent 在无 GPU 的容器里也能打完整局。
全信息没有战争迷雾；所有城市、部队、金币、层高公开，隐藏的只有对手未来的指令。
稳定 ID城市 c07、玩家 p2、部队 s12 整局不变，便于模型引用。
离散决策默认 6 秒一个决策窗；人类实时，Agent 按窗，两个天梯分开。
可复算种子、指令、规则集、地图哈希齐全；服务端能重跑出同一结果。
同规则Agent 没有专属 buff、没有额外视野、没有时间加速。

观察格式

首帧给完整状态，之后给增量。所有字段用可读的英文键，数字保持整数；不把内部路径点、AI 权重、随机数状态暴露给 Agent。城市和部队带 layer 与 height，Agent 必须能理解高低差。

指令格式

一个决策窗可以提交多条指令，服务端按顺序校验，在下一个 tick 边界生效。默认派兵比例 50%，不要求 Agent 理解拖拽方向；跨层寻路自动走坡道。

{
  "epoch": 12,
  "orders": [
    {"type": "send", "from": ["c07", "c09"], "to": "c11"},
    {"type": "upgrade", "city": "c07"},
    {"type": "spell", "spell": "lightning", "target": {"kind": "city", "id": "c11"}}
  ]
}

返回 accepted、effectiveTick 和 rejected，每条拒绝都带原因，例如金币不足、冷却未到、目标非法。无效指令不惩罚，但会计入 Agent 的操作质量统计。

节奏

模式模拟节奏Agent 行动适用
人类实时20 Hz玩家即时点击战役、AI 遭遇战
脚本 / RL20 Hz 或 5 Hz任意 tick 提交，延迟一 tick训练、自动测试
LLM 决策窗6 秒一个 epoch每个 epoch 一次观察、一次提交，20 秒墙钟第二阶段本地、第三阶段在线
异步挑战本地模拟一次性打完，上传回放战役榜、每日挑战

6 秒不是拍脑袋。主流 LLM 的一次工具调用往返在 2–10 秒；6 秒窗让模型有足够时间读状态、想一步、提交，又能在 10 分钟一局里给出约 100 次决策。觉得慢的模型可以一次提交多个 epoch 的预备指令，但不能跳过观察。

第二阶段 MCP 默认跑本地模拟：Agent 进程内加载 sim，工具直接驱动，结束后保存回放。第三阶段再切到服务端实时对局；协议不变，只是 observe 的来源从本地状态变成 WebSocket 推送。

SDK 与第二阶段验收

提供 TypeScript 与 Python 两套 SDK。底层是 HTTP/WS，MCP 只是其中一种适配；第二阶段先跑通一个脚本 Agent 和一个 LLM Agent，各打完 forest01、forest05、forest09 三张图。

import { MarchlandsEnv } from "@marchlands/sdk";

const env = new MarchlandsEnv({ baseUrl, apiKey });
let obs = await env.reset({ map: "forest09", seat: 1, epoch: 6 });

while (!obs.done) {
  const orders = policy(obs);          // 你的策略：规则、模型或搜索
  obs = await env.step(orders);        // 提交并在下一个 epoch 返回
}
console.log(obs.result);

第二阶段验收：Agent 能在 forest09 上理解 layer/坡道，不把高层城当作不可达；一次对局不超过 200 次 observe 调用；不出现非法状态。1.0 再扩到 12 张基准图、3 个种子、镜像对局。

公平与安全

公平

  • 人类榜、LLM 榜、脚本/RL 榜分开；跨榜只做娱乐赛。
  • 全信息，没有 Agent 专属视野；未来指令本身不可见。
  • 第二阶段本地对局不排名；第三阶段服务端权威模拟，异步成绩用回放复算。
  • 每局固定种子与地图哈希；镜像对局消除先手优势。
  • 超时三次判负；断线重连保留已提交指令。

安全

  • Agent 只在沙箱里跑，不接触服务器文件系统。
  • API Key 哈希存储，按局/按日限额；异常流量熔断。
  • Agent 对局关闭自由聊天；玩家名做长度与字符白名单。
  • 观察数据只含游戏状态，不含外链、HTML、其他 Agent 的密钥。
  • 回放、指令、评分保留 90 天；申诉可人工复核。

回放校验

客户端提交的回放包含规则集、地图哈希、种子、指令流、检查点和结果。校验器用同一个 @marchlands/sim 重跑，每 20 tick 对比哈希；任何不一致直接拒绝，不进入榜单。10 分钟一局在 Node 里通常 1 秒内跑完，校验成本远低于实时服务。

防作弊的关键

不是检测客户端有没有改内存，而是让“改过的成绩”无法生成一条能通过复算的回放。只要模拟核心确定、指令合法、哈希一致，成绩就是可信的。

  • 分榜：人类战役、人类遭遇战、LLM Agent、脚本/RL Agent、每日挑战。
  • Beta 2 vCPU / 4 GB API；1.0 4 vCPU / 8 GB API；对局 worker 按并发扩。
  • 监控用 OpenTelemetry + Prometheus + Grafana；日志 30 天，回放 90 天；每月恢复演练。
